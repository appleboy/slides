為什麼需要 MCP Gateway？

MCP Authorization 的流程很複雜，開發者其實不需要知道這麼多細節。

MCP Authorization 規範要求的完整握手：從 401 到 200
  1. 1Client → GatewayGET /mcp (no token)
  2. 2Gateway → Client401 + WWW-Authenticate: resource_metadata
  3. 3Client → GatewayGET /.well-known/oauth-protected-resource
  4. 4Client ⇄ IDPAuth Code + PKCE → RS256 access token
  5. 5Gateway → IDPfetch JWKS (cached / auto-rotated)
  6. 6Gatewayverify: sig(JWKS) + iss + aud + exp + scope
  7. 7Gateway → Serverforward + X-MCP-Subject / X-MCP-Scope
交給 MCP Gateway

開發者不用懂

  • OAuth 授權流程PKCE
  • JWT 驗證iss / aud / exp
  • JWKS 快取與輪替RS256
只專注寫好 MCP 本身

規範：modelcontextprotocol.io/specification/2026-07-28/basic/authorization

AuthGate 要解決的問題

MCP、Skill 服務、Bot、Web 工具、CLI 各自實作認證，帶來三個問題。

1

認證各自造輪子

  • 每個服務自己接 LDAP
  • 密碼規則、bind 帳密散落各處
  • LDAP 異動，所有服務得一起改
  • 沒有統一的登入紀錄
2

Token 發出去就沒人管

  • 誰有有效 Token？答不出來
  • 何時過期？能不能撤銷？
  • 沒有 refresh 輪替與到期政策
  • 出事時沒有快速撤銷的路
3

服務擁有者看不到誰在用

  • 誰有權限使用這個服務？
  • 何時授權、何時到期？
  • 核准了哪些 scope？
  • 稽核報表得翻散落的日誌

個人 API 金鑰

用在哪

  • 腳本與自動化流程，不必每次互動登入

怎麼控管

  • 名稱、到期時間、上次使用都看得到

  • 隨時撤銷，依狀態篩選
